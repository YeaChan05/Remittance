### Shared Testcontainers

멀티 모듈 프로젝트에서 통합 테스트는 보통 각 태스크가 독립적으로 컨테이너를 띄우는 방식으로 시작한다

이 방식은 단순하지만 태스크 수가 늘어날수록 다음 문제가 커진다

- 같은 종류의 컨테이너를 여러 번 띄우면서 실행 시간이 길어진다
- repository 수준 테스트와 application 수준 테스트가 서로 다른 초기 상태를 보게 된다
- BOM 버전이나 런타임 classpath가 어긋나면 특정 태스크에서만 재현되는 오류가 생긴다

현재 프로젝트는 이 문제를 테스트 코드가 아니라 `build-logic`의 공통 플러그인에서 해결한다

#### 1. 기본 아이디어

컨테이너를 개별 테스트 클래스의 책임으로 두지 않고, **Gradle 태스크 실행 계획의 일부**로 취급한다

- 어떤 태스크가 어떤 컨테이너를 사용하는지 DSL로 선언한다
- 같은 실행 스택(stack)에 속한 태스크는 같은 컨테이너를 공유할 수 있다
- 필요한 경우 특정 컨테이너만 격리(isolate)할 수 있다
- 실행 계획에 포함된 모든 관련 태스크가 끝나면 공유 컨테이너를 정리한다

즉, 테스트 인프라를 테스트 코드에서 중복 구현하지 않고 build-logic에서 일관되게 관리한다

#### 2. 선언 방식

각 모듈은 자신이 필요한 컨테이너와 공유 범위를 아래처럼 선언한다

```kotlin
testcontainers {
    bom("org.testcontainers:testcontainers-bom:2.0.3")

    task("integrationTest") {
        stack("core")
        use("mysql")
        use("rabbitmq")
        isolate("mysql")
        liquibase("classpath:/db/changelog/db.changelog-master.yaml")
    }
}
```

- `bom(...)`: 해당 태스크군이 따라야 하는 Testcontainers BOM 버전이다
- `task(...)`: 공유 컨테이너 정책을 적용할 Gradle 태스크 이름이다
- `stack(...)`: 어떤 태스크끼리 컨테이너를 공유할지 결정하는 논리적 그룹이다
- `use(...)`: 필요한 컨테이너 종류를 선언한다
- `isolate(...)`: 같은 stack 안에서도 이 컨테이너는 독립 인스턴스를 사용하도록 한다
- `liquibase(...)`: 컨테이너가 준비된 뒤 적용할 schema/change log를 지정한다

#### 3. 실행 원리

공통 플러그인은 Gradle `BuildService`를 사용해 공유 컨테이너의 수명주기를 관리한다

1. 태스크 그래프가 확정되면 어떤 태스크들이 실제로 실행될지 계산한다
2. 같은 `stack`과 같은 provider scope를 공유하는 태스크를 하나의 생명주기 owner로 묶는다
3. 첫 태스크 실행 전에 필요한 컨테이너를 준비한다
4. 같은 owner에 속한 후속 태스크는 이미 떠 있는 컨테이너를 재사용한다
5. 해당 owner에 속한 모든 태스크가 종료되면 컨테이너를 정리한다

이 구조의 핵심은 “컨테이너를 태스크 하나에 귀속시키지 않는다”는 점이다
실행 계획 전체를 보고 공유 여부를 결정하므로, 테스트 순서와 재사용 범위를 한 곳에서 통제할 수 있다

#### 4. 추가 검증

공유 컨테이너를 도입하면 버전 어긋남이 더 치명적일 수 있다

그래서 현재 프로젝트는 런타임 classpath를 검사해 아래 상황을 조기에 차단한다

- 선언한 BOM 버전과 다른 Testcontainers 모듈이 섞여 있는 경우
- 특정 provider가 기대하는 모듈이 다른 버전으로 해석된 경우

이 검증은 테스트 실행 전에 실패하게 하여, 애매한 런타임 오류 대신 명확한 build 오류로 드러내는 역할을 한다

#### 5. 장점

- 테스트 코드에서 컨테이너 부트스트랩 로직을 반복 작성하지 않아도 된다
- 같은 스택의 태스크가 동일한 인프라 조건을 공유할 수 있다
- 필요한 컨테이너만 선택적으로 격리할 수 있다
- 버전/BOM 불일치를 빌드 단계에서 빠르게 검출할 수 있다
- 테스트 인프라 정책을 Gradle DSL로 선언하므로 프로젝트 규모가 커져도 일관성을 유지하기 쉽다

#### 6. 주의할 점

- 공유 범위를 너무 넓게 잡으면 테스트 간 간접 결합이 생길 수 있다
- 반대로 모든 컨테이너를 무조건 `isolate(...)` 하면 공유의 이점이 줄어든다
- 데이터베이스 상태는 공유하더라도, 테스트 데이터 초기화 전략은 별도로 가져가야 한다
- 이 방식은 “컨테이너를 재사용해도 되는 테스트”에 특히 잘 맞는다
  테스트가 강하게 독립된 환경을 요구하면 격리 전략을 우선 고려해야 한다

#### 7. 언제 유용한가

- 멀티 모듈 Spring Boot 프로젝트
- repository/application/integration test가 공통 인프라를 공유하는 프로젝트
- MySQL, RabbitMQ, Kafka 같은 컨테이너성 의존이 많은 프로젝트
- 테스트 인프라 정책을 코드가 아니라 build-logic에서 중앙 관리하고 싶은 프로젝트
